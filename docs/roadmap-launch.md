# 三端上线执行计划与时间表

> **文档性质：** 初审用落地计划（方案设计阶段）  
> **目标：** Web + Android + iOS 互通上架  
> **基准：** 当前已有可运行的 Web + Express API 试验版（目标/契约/JWT/通知等）  
> **版本日期：** 2026-07-25  

本文回答：若要把现有能力做成**可正式上线、三端共用账号与数据**的产品，大致要多久、分哪些阶段、每个模块怎么排。

---

## 0. 结论先看（给评审）

| 情景 | 团队假设 | 到「三端可上架可用」的粗估 |
|------|----------|----------------------------|
| **A. 紧凑上线** | 2～3 人全职（1 后端兼架构、1 Web、1 移动） | **约 7～10 个月** |
| **B. 稳健上线** | 同上，含缓冲、合规与两轮公测 | **约 10～14 个月** |
| **C. 单人主扛** | 1 人全栈兼职移动 | **约 14～20 个月**（或砍范围） |

**推荐对外承诺口径（初审）：**  
以 **B 方案 12 个月** 为基线排期；前 4 个月必须先把「账号 / 数据 / API / Web 生产化」夯实，再铺移动端，否则三端会反复返工。

```
现在 ──► 生产级后端+Web ──► 移动端共建 ──► 内测/商店审核 ──► 正式上架
试验版      (约 3～4 月)        (约 4～5 月)     (约 2～3 月)
```

---

## 1. 前提与范围

### 1.1 已有（可复用）

- Web（Next.js）+ API（Express + SQLite）
- 注册登录 JWT、目标/奖励/契约、通知、见证人、AI 填表试验能力
- 工程文档与 monorepo 骨架

### 1.2 上线必须补齐（相对现状）

| 类别 | 内容 |
|------|------|
| 账号 | 正式邮件、可选手机号验证、刷新令牌、风控、注销账号 |
| 数据 | 迁出单机 SQLite → 托管 Postgres（或等价）；备份与迁移 |
| 客户端 | 正式 Web；Android / iOS 原生壳或跨端 App |
| 互通 | 同一账号、同一 API、推送（APNs / FCM）、冲突策略 |
| 质量 | 自动化测试、监控告警、性能与安全基线 |
| 合规上架 | 隐私政策、用户协议、应用商店材料、国内若上架还需备案等评估 |
| 运营 | 灰度、客服入口、版本强更策略 |

### 1.3 明确不做（第一版可砍，避免排期爆炸）

- 法律级电子签 / 存证链（可放二期）
- 复杂社交动态/Feed
- 完整商业化计费（可先免费 + 内测）
- Java 微服务全面替换 Node（可并行规划，不挡上线）

### 1.4 三端技术选型建议（影响工期）

| 方案 | 工期影响 | 说明 |
|------|----------|------|
| **推荐：React Native / Expo** | 中 | 与现有 TypeScript 栈近；一套业务逻辑两商店 |
| Flutter | 中 | 表现力好，但团队需补 Dart |
| 双端原生 | 很长 | +4～8 月，初审不建议 |
| 仅 PWA + 加桌面 | 最短但不算「上架 App」 | 可作过渡，难进部分商店能力（推送等受限） |

下文工期按 **「现有 API 演进 + Web 生产化 + RN/Expo 双端」** 估算。

## 2. 总体阶段时间表

按 **稳健上线（约 12 个月）** 排；括号内为紧凑版可压缩周数。

| 阶段 | 名称 | 周期 | 累计月末 | 阶段目标 |
|------|------|------|----------|----------|
| **P0** | 基线冻结与方案确认 | 2 周 | 0.5 | 范围、选型、里程碑、人员确认 |
| **P1** | 后端生产化与账号体系 | 8～10 周（6） | 3 | 可支撑多端的稳定 API + 正式账号 |
| **P2** | Web 生产就绪 | 6～8 周（4）与 P1 后半重叠 | 4.5 | Web 可公网灰度 |
| **P3** | 移动端 MVP（功能对齐核心） | 12～16 周（10） | 8.5 | Android/iOS 内测包 |
| **P4** | 三端互通与体验统一 | 4～6 周（3） | 10 | 账号/数据/推送打通验收 |
| **P5** | 质量、合规、上架 | 6～8 周（4） | 12 | 商店过审 + 正式发布 |

## 3. 分阶段 × 分模块执行计划

### P0｜基线冻结（2 周）

| 模块 | 工作项 | 产出 | 建议人天 |
|------|--------|------|----------|
| 产品 | 上线范围 PRD（Must/Should/Could） | 范围表 | 3 |
| 架构 | 三端架构图、API 版本策略 | ADR | 3 |
| 移动 | 选定 RN/Expo 或 Flutter | 选型结论 | 2 |
| 合规 | 隐私字段清单、是否收集手机号 | 初稿 | 2 |
| 工程 | 环境：dev/staging/prod | 仓库与域名 | 3 |

**关口：** 签字确认「V1.0 必做清单」；未进清单的一律二期。

---

### P1｜后端生产化与账号（8～10 周）

目标：任何一端只对接 **同一套生产级 API**。

| 模块 | 工作项 | 周期（周） | 依赖 |
|------|--------|------------|------|
| **数据层** | SQLite → Postgres（或云 SQLite 托管评估）；迁移脚本；备份 | 2～3 | — |
| **账号安全** | Refresh Token；密码策略；登录限流；设备会话列表（可选） | 2 | 数据层启动后 |
| **邮件** | 注册验证（可选）、重置密码真发信、模板 | 1～2 | 邮件服务商 |
| **手机号**（若 V1 要） | 短信验证码登录/绑定 | 2 | 短信服务商、资质 |
| **资料与注销** | 注销账号、导出数据（合规常见要求） | 1 | 账号 |
| **业务 API 硬化** | 分页、幂等、错误码规范、OpenAPI 文档 | 2 | 与上并行 |
| **通知服务** | 服务端推送管道抽象（为 APNs/FCM 预留） | 1～2 | — |
| **观测** | 日志、错误追踪、基础指标、健康检查 | 1 | — |
| **环境** | Staging 独立库；密钥与 CI | 1～2 | — |

**关口：** Staging 上完成「注册→绑邮箱→重置密码→目标全流程」压测与安全自查；SQLite 不再作为生产主库。

---

### P2｜Web 生产就绪（6～8 周，与 P1 后半重叠）

| 模块 | 工作项 | 周期（周） |
|------|--------|------------|
| **体验** | 空态/错态/加载；移动浏览器适配；关键路径埋点 | 2 |
| **性能** | 首屏、列表分页、图片与缓存策略 | 1～2 |
| **安全** | XSS/CSRF 面、CSP、依赖审计 | 1 |
| **运营页** | 隐私政策、用户协议、关于与反馈入口 | 1 |
| **发布** | 前端 CI/CD、预发域名、回滚 | 1 |
| **灰度** | 邀请制或功能开关 | 1 |

**关口：** 公网 Staging/预发 Web 稳定跑通核心故事；与 API 契约冻结一版（如 `/api/v1`）。

---

### P3｜移动端 MVP（12～16 周）

对齐 **V1.0 核心**：账号、首页、目标闭环（含兑现）、契约基础、通知、我的。  
契约复杂编辑、AI 语音等可标为 Should，视进度裁剪。

| 模块 | 工作项 | 周期（周） | 备注 |
|------|--------|------------|------|
| **工程脚手架** | RN/Expo 工程、鉴权存储、API Client、导航 | 2 | |
| **账号** | 登录注册、重置、资料、注销 | 2 | 复用 API |
| **首页 + 目标** | 列表、详情、进度、达成、兑奖 | 3～4 | 核心路径 |
| **契约** | 列表 + 详情 + 条款状态 | 2～3 | 可简化创建 |
| **通知** | 列表、已读；对接推送权限 | 1～2 | |
| **推送** | FCM + APNs 证书/配置、打通服务端 | 2 | 常踩坑，留缓冲 |
| **我的** | 资料、信任分展示 | 1 | |
| **双端打磨** | iOS/Android UI 差异、权限文案 | 2 | |
| **内测分发** | TestFlight + 内测轨道（Google Play） | 1 | |

**关口：** 封闭内测（建议 ≥20 人）跑完「建目标→兑现」；崩溃率与登录成功率达标（自定阈值）。

---

### P4｜三端互通与体验统一（4～6 周）

| 模块 | 工作项 | 周期（周） |
|------|--------|------------|
| **数据一致性** | 多端同时操作冲突策略（以服务端为准） | 1～2 |
| **会话** | 多端登录、踢下线策略（产品定） | 1 |
| **推送一致性** | Web（若做）/ App 通知与站内信对齐 | 1 |
| **设计统一** | 组件与文案、空态、错误提示三端一致 | 1～2 |
| **版本策略** | App 最低版本、强制更新接口 | 1 |
| **回归** | 三端同一套用例手工 + 冒烟自动化 | 1～2 |

**关口：** 「同一账号 Web 建目标 → 手机收到通知并兑现」全链路演示通过。

---

### P5｜质量、合规、上架（6～8 周）

| 模块 | 工作项 | 周期（周） | 风险 |
|------|--------|------------|------|
| **测试** | 用例库、回归、兼容机型、弱网 | 2～3 | |
| **安全** | 渗透或第三方基线、密钥轮换 | 1～2 | |
| **合规文案** | 隐私政策、权限说明、儿童/算法（若适用） | 1～2 | 法务评审 |
| **商店资产** | 截图、描述、分级、隐私问卷 | 1 | |
| **Apple 审核** | 提交、拒审修改、再提 | 1～3 | **拒审常见，必须留缓冲** |
| **Google Play** | 提交、政策表单 | 1～2 | |
| **国内上架加项**（若做应用商店/备案） | 主体、软著、备案等 | **另计 1～3 月** | 与海外商店可并行规划 |
| **正式发布** | 生产切换、监控值班、回滚演练 | 1 | |

**关口：** App Store + Google Play 均「可下载」；Web 生产域名正式开放；有监控与值班。

> **重要：** 若目标含**国内安卓应用商店 + ICP/备案**，请在 12 个月基线上 **再加 1～3 个月** 或从 Day 1 并行办资质，否则「上架」定义会被行政流程拖住。

## 6. 风险与缓冲（评审必看）

| 风险 | 影响 | 缓解 |
|------|------|------|
| 商店拒审（尤其 iOS） | +2～6 周 | 提前对照 Guideline；登录若仅用户名需说明；隐私问卷一次填对 |
| 推送证书 / 国内厂商通道 | 移动延期 | 早期打通 FCM/APNs；国内另评估厂商推送 |
| 过早做微服务 / 换 Java | 整体延期 | V1 坚持单一业务 API 集群 |
| 范围膨胀（社交、支付、AI） | 无限延期 | Must 清单冻结；变更走变更单 |
| 单人瓶颈 | 进度腰斩 | 关键路径双人备份；移动可外包壳 + 自研业务 |
| 合规与备案 | 「上不了架」 | 提前确认上架地区与主体资质 |

**建议缓冲：** 总日历中保留 **15%～20%** 不可排任务周（已部分含在 B 方案 12 个月里）。

## 8. 与「现在就开始」的下一步（2 周内）

1. 召开范围会：敲定 V1 Must 列表与三端选型（建议 Expo/RN）。  
2. 申请域名、云账号、邮件/短信服务商。  
3. 建立 staging；列出 Postgres 迁移任务拆解。  
4. 同步更新本计划的「责任人 / 起止日期」列（本文为基线模板）。  
5. 对外介绍文档、PPT 与本计划解耦：计划进工程文档，介绍进产品文档。

---

## 9. 一句话汇报稿

> 现有 Web 试验版可复用约 30%～40% 的业务与认知；要做成 **Web + Android + iOS 互通并正式上架**，在 2～3 人全职、范围受控前提下，**稳健排期约 12 个月**（紧凑 7～10 个月，含国内备案则可能再加 1～3 个月）。节奏上必须 **先生产级后端与账号，再 Web 灰度，再移动双端，最后合规上架**，否则三端互通会成倍返工。
